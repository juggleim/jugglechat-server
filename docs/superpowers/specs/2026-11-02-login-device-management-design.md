# 登录设备管理设计

> 2026-11-05 用户确认变更：当前契约为“只撤销当前业务会话 + 精确设备 IM kick，立即允许重新登录”。本文已更新当前规则；旧实施计划中的十分钟 ban 仅为历史，不再执行。接入与隔离边界见 `docs/deviceauth-im-integration.zh-CN.md`。

## 目标与范围

为一个用户管理多台登录设备，满足以下能力：

- 按最后登录时间倒序列出登录设备。
- 将设备按 IM 在线和离线状态分组返回。
- 删除非当前设备时，立即使其业务登录态失效并强制其 IM 连接下线，允许立即重新登录。
- 沿用既有登录 URL，仅扩展登录请求参数。

操作范围为 `(app_key, user_id, device_id, target_session_id)`。不调用 IM ban/unban，不清理运营封禁，不使 IM 旧凭据永久失效。客户端安装标识不是不可伪造的物理设备身份。

过渡期允许旧版本登录，但不能可靠关联旧会话与设备，因此只管理新设备会话，不承诺严格设备身份防绕过。

不在本次范围内：删除当前设备、批量删除设备、设备重命名、历史登录地点/IP 展示、可配置封禁时长。

## 现状与问题

初始实现中业务 token 的 device_id 未赋值且无会话持久化。因此新增持久化设备/session、ds1 token 和 IM 设备维度在线查询及 kick。当前规则以本文及接入说明为准，不保留十分钟封禁功能。

## 客户端登录请求

以下真正签发登录态的既有接口增加统一的设备字段，保留原有字段和 URL：

- `POST /jim/login`
- `POST /jim/sms/login`
- `POST /jim/sms_login`（保留既有别名，共用相同逻辑）
- `POST /jim/email/login`
- `POST /jim/login/qrcode/check`

请求字段：

```json
{
  "device_id": "稳定的客户端安装标识",
  "device_name": "Fei 的 iPhone",
  "platform": "ios",
  "os_version": "iOS 18.1",
  "app_version": "1.0.0"
}
```

新设备会话要求 `device_id` 与 `platform` 同时提供有效值；过渡期两者均未提交时允许使用旧版登录流程，截止后两者均必填。只提交其中之一、提交空值或非法值均返回参数错误，不得降级为旧版登录。`device_name`、`os_version`、`app_version` 为选填展示字段，缺失不阻断登录。服务端限制 `device_id` 为 128 字符、`platform` 为 32 字符、设备名称为 128 字符、版本字段各为 64 字符，拒绝控制字符与超长值。平台使用受支持的枚举值，不接受任意无界字符串。

设备 ID 必须在同一次安装生命周期内稳定，并与 IM 实际连接标识一一对应。实施前先核对 IM 客户端 SDK 的设备 ID 获取/设置能力，不能另造一个与 IM 无关的 UUID。

二维码场景采用已确认的方案 A：待登录的新设备在每次 `POST /jim/login/qrcode/check` 请求中提交设备字段；`POST /jim/login/qrcode/confirm` 不创建新设备记录。二维码单次兑换与重试规则见后文。

## 数据模型

新增 `user_devices` 表，每行表示 `(app_key, user_id, device_id)` 的一个受管理设备：

| 字段 | 说明 |
| --- | --- |
| `id` | 自增主键 |
| `app_key` | 应用隔离键 |
| `user_id` | 所属用户 |
| `device_id` | 客户端设备/安装标识 |
| `device_name` | 设备展示名 |
| `platform` | 平台，例如 `ios` |
| `os_version` | 系统版本 |
| `app_version` | 客户端版本 |
| `last_login_time` | 最近成功登录的毫秒时间戳 |
| `last_active_time` | 最近业务请求通过鉴权的毫秒时间戳；无记录时为 null，不冒充 IM 活跃时间 |
| `session_id` | 服务端生成的随机会话 ID；每次新登录更换，删除后撤销 |
| `state` | `active`、`revoking`、`revoked` |
| `revoke_operation_id` | 最近一次删除操作 ID，用于 IM 调用幂等和后台补偿 |
| `banned_until` | deprecated 历史列；不检查、不写新设备封禁，不在 API 输出 |
| `deleted_at` | 删除时间；保留记录以支持审计 |
| `created_time` / `updated_time` | 数据库时间 |

唯一索引为 `(app_key, user_id, device_id)`；列表索引为 `(app_key, user_id, deleted_at, last_login_time DESC)`。

删除不是物理删除。active/revoking/revoked 均可通过有效新登录创建全新 session 并恢复 active；历史 banned_until 不参与判断。旧 ds1 token 永远不能恢复有效。一个设备只保留一个当前业务会话。

## 认证与登录流程

1. 所有四类登录路径在完成凭证验证后统一判断设备参数与迁移阶段：完整设备参数进入 `IssueDeviceLogin`；两项身份字段均未提交且尚在兼容期时进入原有登录/token 签发流程，不伪造设备记录。账号密码、短信（含别名）、邮箱及二维码状态检查成功分支共用此规则。
2. 完成原有账号凭证验证后，在设备状态事务中锁定 `(app_key, user_id, device_id)`，不因 revoking 或历史 banned_until 拒绝登录。
3. 原子创建/更新设备记录，生成全新随机 session，更新设备资料、last_login_time，恢复 active；与正在执行的 kick 锁同一行。
4. 专用用户会话签发函数把 `device_id`、`session_id` 以及明确的用户会话凭证类型写入业务 token；令牌序列化/加密失败必须返回错误，不能返回空 token 并宣称成功。
5. 新用户会话鉴权校验 token 的应用、凭证类型、active、未删除及当前 session 一致，不检查 banned_until。任一失败不得回退旧鉴权。撤销后即使重新登录，旧 token 永久无效。只有完全缺少新身份的有效旧格式 token 才按兼容策略处理。
6. `last_active_time` 仅表示业务鉴权时间，每设备约每分钟节流更新；不用于 IM 在线判断。Authenticate 在设备行锁事务内校验当前 session 并按需更新活动时间，与撤销/轮换串行化；节流不更新仍成功，不用 RowsAffected=0 判断无效。无延迟失效的认证正缓存；鉴权完成后的在途业务执行不承诺回滚。

### 并发与会话一致性

登录与删除使用同一 MySQL InnoDB 设备行锁及唯一键冲突重试。Process 锁序为设备 → 任务，核对 target session/operation 后，持锁执行最多约五秒 context 的 IM 调用及离线核查；该副作用事务不自动重试。登录先提交，旧任务完成 superseded、不发 kick；kick 先持锁，同设备登录短暂等待后签发新 session。新一次按 device_id 的删除仍删除执行时当前会话，不得自动重放到已重登目标。

DB 锁覆盖跨业务进程检查到发送的窗口，不是远端执行屏障。IM 无 session 条件，超时或异步延迟执行仍可能踢到新连接，旧 IM token 也可能自行重连；不能保证零风险或绝对无阻塞。客户端收到 kick 通知应停止自动重连，允许用户主动新登录。发布需停旧版实例/worker 统一切换。

### 二维码单次兑换与重试

二维码记录增加 `pending/confirmed/consumed` 状态、领取设备 ID、领取会话 ID 和首次成功兑换时间。生成二维码时，额外返回随机的 `poll_secret`；新设备保存它并在 `check` 中提交，服务端仅存其哈希，二维码图中不包含该秘密。确认扫码仍只使用原有二维码 ID 与当前登录态。

设备参数仍从 `check` 获取。首次成功兑换须验证 `poll_secret`，并在同一数据库事务中将二维码从 `confirmed` 原子变更为 `consumed`、绑定该设备及新会话、更新设备最后登录时间。不同设备或不正确的秘密不能领取同一二维码。重复扫码确认不得把已消费状态恢复为可兑换状态。

二维码流程也需兼容：过渡期保留无设备参数、无 `poll_secret` 的旧版二维码领取路径；其登录态不纳入设备管理，且不得领取已经绑定新设备会话的二维码。二维码首次有效领取时原子确定旧模式或新模式，之后不可互相降级/切换。旧模式维持既有客户端协议，不宣称具有新模式的设备绑定和单会话安全保证。严格阶段关闭旧领取路径，要求设备参数与 `poll_secret`。旧用户 token 在过渡期可继续调用二维码确认接口以保持既有扫码功能，但不能因此取得设备管理权限；严格阶段确认接口也只接受新用户设备会话。

在原有二维码十分钟有效期内，持有正确秘密的同一设备可重试领取同一会话结果；不得轮换 `session_id`、重复更新登录时间或创建新设备。返回凭证必须属于同一会话；重试时需再次校验会话仍有效，已撤销则拒绝，不能凭二维码重新激活。重试结果需在安全的限时结果存储中保留，不能在普通日志或明文审计数据中存储 token。过期后拒绝领取并清理结果。客户端收到成功结果即停止轮询。

### 用户会话与服务凭证隔离

现有 `apis/assistantmsgcallback.go` 也调用 token 签发函数，不能把该内部调用强行绑定实体设备。区分用户会话与内部服务凭证的签发入口和凭证类型；内部服务凭证应有短有效期、明确受众和最小权限允许列表，不允许伪装用户会话。

`devices/list`、`devices/del` 只接受有效的新用户设备会话；二维码确认接口按迁移阶段接受用户会话。三者均不接受 API Key 或内部服务凭证。保留现有 API Key 集成所需的明确授权路径；旧用户 token 仅在过渡期和明确兼容的接口范围内放行。实施前逐一核对助手调用依赖的下游接口；未完成服务凭证适配不得直接替换公共签发函数。

### 分阶段兼容与发布

由服务端按应用统一配置 `device_auth_required_at`，截止时刻必须在严格启用前由发布负责人设定并向用户通知；不从客户端版本号决定是否强制校验，也不在文档中虚构具体上线日期。

| 场景 | 截止前：兼容阶段 | 截止后：严格阶段 |
| --- | --- | --- |
| 完整有效设备参数登录 | 签发新设备会话 token | 签发新设备会话 token |
| 两项设备身份参数均未提交 | 原有登录流程与旧 token 格式 | 拒绝并提示升级 |
| 只提交部分、空值或非法设备身份参数 | 拒绝，不降级 | 拒绝 |
| 有效旧用户 token 访问普通业务接口 | 保持原有权限校验与行为 | 拒绝，要求升级并重新登录 |
| 旧 token 访问设备列表/删除 | 拒绝，提示使用新版重新登录 | 拒绝 |
| 旧 token 确认二维码 | 兼容已有行为 | 拒绝 |

发布顺序：先完成新老凭证分流、客户端参数支持、IM 能力验证及内部服务适配；上线兼容阶段并积累设备记录，监测不含凭据的旧登录/旧鉴权使用量；公告截止时间；最后统一关闭旧登录签发、旧 token 鉴权及旧二维码领取，不能只关闭其中一项。不得回滚为让已撤销的新会话走旧鉴权。

兼容阶段的列表仅包含可识别的新设备会话，不虚构旧设备，也不代表全部登录设备。页面需说明旧版本登录暂不支持设备管理；新客户端持旧 token 时重新登录后管理。省略设备身份的旧登录无法可靠关联撤销目标，因此不提供严格设备身份防绕过保证。

## 新增业务接口

### `GET /jim/devices/list`

仅查询当前新设备会话 `Authorization` 所属用户的未删除设备。不接收其他 `user_id`，禁止跨用户读取。兼容阶段不包含无法识别设备的旧版登录态。

服务端向 IM 的**设备维度**在线状态能力查询，优先批量获取当前用户的在线设备，再与本地活跃设备记录合并，分为 `online_devices` 和 `offline_devices`。只展示 `state=active` 且未删除的记录。每组按 `last_login_time` 倒序排列，时间相同时按 `device_id` 升序稳定排序；`is_current_device` 由已验证 token 的 `device_id` 比较得出。IM 不支持批量时使用有限并发和统一超时，不能无界逐台请求。

响应 `data`：

```json
{
  "online_devices": [
    {
      "device_id": "...",
      "device_name": "Fei 的 iPhone",
      "platform": "ios",
      "os_version": "iOS 18.1",
      "app_version": "1.0.0",
      "last_login_time": 1760000000000,
      "last_active_time": 1760000100000,
      "is_current_device": true
    }
  ],
  "offline_devices": []
}
```

IM 在线状态查询失败时整个接口返回可重试的 IM/内部超时错误，不返回可能错误的在线分组。

### `POST /jim/devices/del`

请求：

```json
{ "device_id": "要删除的设备 ID" }
```

仅可操作当前用户的设备。目标不存在或属于其他用户时返回相同的设备不存在错误；与当前 token 的 `device_id` 相同则返回禁止删除当前设备。删除完成后的重复请求返回成功；撤销中的重复请求必须恢复未完成操作，不能直接成功。普通登出不使用此接口。

成功删除的顺序：

1. 事务锁设备，设置 revoking/deleted_at，保存新 operation ID 和 target session，立即使旧业务 token 失效。已鉴权在途请求不承诺回滚。不写新设备封禁。
2. Process 在上述锁内核查是否 superseded；否则完整查询当前 IM 设备在线状态，离线原设备可成功；仍在线则精确 kick 单设备并再次查询离线。
3. 仅 kick 异步应答不能完成；核查满足后条件更新 revoked/done。成功 data 为 operation_id、status=completed；新登录替换目标则 status=superseded，不宣称踢线完成。
4. IM 未确认返回 17606，status=pending；持久化任务供恢复。存储故障返回 17600，不能仅凭 operation_id 判断已提交。

同一目标会话复用操作 ID；历史带期限任务也只走 kick/离线核查，旧期限不阻断恢复。绝不调用 ban/unban，既有运营封禁不自动解除。离线核查只说明当前状态，不能证明特定 session 已被踢。

该接口按设备定义为“删除调用执行时的当前会话”：同设备立即完成全新登录后再次提交删除属于新操作。观察到重新登录后必须停止旧请求重试；后台补偿只处理旧 operation/target session。

## IM SDK 集成前置条件

当前仓库使用 `github.com/juggleim/imserver-sdk-go v1.0.16`，源码未调用设备级状态或踢下线 API。实施前必须在 SDK 文档或其可访问源码中确认下列能力与准确方法签名：

1. 基于 `user_id + device_id` 查询在线状态（不能只返回用户整体在线）。
2. 基于 `user_id + device_id` 强制断开该设备的 IM 长连接。
3. 客户端连接 IM 时能携带与业务 `device_id` 一致的值，使 IM 识别为同一设备。
4. 不全局撤销共享 IM token，不调用 ban/unban；旧业务 token 永久失效。
5. 当前 IM 无 session 条件，延迟 kick 隔离/可靠执行确认需上游能力；真实连接和隔离须联调。

当前只复用在线查询及 kick 接口。device_im_kick_enabled 默认 false；新键优先，缺失才 fallback 到弃用 device_im_ban_enabled（旧 true 仅开启 kick）。false 返回 IM 未确认，不静默成功。真实设备身份、断连、延迟 kick 和隔离尚需联调。

## 错误与安全规则

- 错误码：设备参数非法、设备不存在、禁止删除当前设备、会话失效、IM 操作未确认；历史 17607 不再由本功能产生。
- 服务端从 token 推导用户和当前设备，绝不相信删除接口中的用户 ID。
- `device_id` 不作为认证凭据；认证仍以签名业务 token 和持久化设备状态为准。
- 删除设备不删除用户账号，也不影响同一用户其他设备。
- 服务端接收的客户端设备名与版本均不作为权限判断依据；安装标识可被重置的限制需在产品安全说明中公开。
- 不记录或输出 `Authorization`、IM token、手机号等敏感凭据。

## 测试范围

- 四类登录（含短信别名）：新参数登记；同设备轮换；revoking/revoked 立即重登，历史期限不阻断。兼容/严格及参数校验保持既有规则。
- 鉴权：有效新会话通过；已删除、部分身份、session 不匹配、跨用户拒绝；历史 banned_until 不参与。已撤销 token 不降级。
- 列表：仅返回当前用户设备；在线与离线分组正确；两组均按最后登录时间倒序；正确标记当前设备；IM 状态查询失败时返回错误。
- 删除：只撤销当前会话和 kick，不调用任何 ban/unban；当前/其他用户/未知目标拒绝。
- IM 集成：精确设备 kick、离线核查、异步应答不完成、原设备离线允许完成，真实连接效果另需联调。
- 生命周期：立即重新登录后旧业务 token 仍永久无效；新删除生成新操作 ID/target session。
- 并发：独立数据库连接验证 kick 持锁时登录等待；新登录先提交则旧任务 superseded，不发 kick。
- 恢复：历史过期任务仍处理；未知响应先核对，任务重放不影响新会话。
- 二维码：不同设备不能重复兑换；同设备丢失成功响应后重试得到同一会话，登录时间不变；已撤销会话、过期二维码及错误秘密均不能兑换；重复确认不能恢复已消费二维码。
- 权限兼容：内部服务凭证/API Key 不可调用设备列表、删除及扫码确认；助手原有授权链路经适配后仍可使用其允许的接口。旧用户 token 仅在兼容期可以扫码确认；新旧二维码领取模式原子确定且不可降级切换，新模式不能被无秘密请求领取。
- 发布切换：同一截止时刻关闭旧登录、旧 token 普通鉴权及旧二维码领取；列表不展示伪造旧设备；检查升级提示、旧使用量监测及新会话无降级规则。记录兼容期省略身份字段可绕过设备关联的已知限制，不将其误报为严格封禁通过。
- IM 边界：不承诺旧 im_token 失效或零延迟误踢风险；真实环境验证其他设备隔离、kick 通知停止自动重连。既有封禁不自动解除。
